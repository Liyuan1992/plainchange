## 1. 产品转向

Change Passport 不再把自己定义为“AI 代码变化解释器”或“更容易使用的代码架构浏览器”。

新的产品定义是：

> 帮助对软件负责、但不具备完整代码掌控力的人，理解 AI 把软件改成了什么样，并决定下一步应该做什么。

核心承诺：

> 你不必读懂所有代码，也能知道 AI 把你的软件改成了什么样。

更锋利的表达是：

> AI 可以替你写代码，但你仍然应该知道它做了什么。

底层仍然可以包含 Git、Diff、AST、模块、静态依赖、测试回执和证据身份；默认界面不要求用户先理解这些概念。

## 2. 问题

AI Coding 正在把三种原本绑定的能力拆开：

1. 能不能做出软件；
2. 能不能理解软件如何工作；
3. 能不能判断一次修改有没有把软件改坏。

Codex、Claude Code 等工具显著降低了第一项门槛，却没有自动解决后两项。目标用户最典型的问题不是“这个类依赖了什么”，而是：

> 它说已经改好了，但我不知道它到底做了什么。

当前 Change Passport 已有受约束证据、通俗变化说明、产品流程图和技术下钻，但默认信息结构仍由代码世界决定：文件、模块、静态关系和框架术语过早出现。它仍然更像“把代码翻译一下”，而不是帮助软件负责人形成判断。

## 3. 目标用户

### 3.1 核心用户

共同特征不是“不会代码”，而是：

> 我不具备完整代码掌控力，但这个软件是我负责的。

包括：

- 使用 AI Coding 的独立开发者；
- 自己用 AI 做产品的产品经理；
- 创业者和小团队负责人；
- 初级开发者；
- 正在转向 AI 工作方式的开发者；
- 大量委托 Codex、Claude Code 完成工作的工程师。

### 3.2 非核心用户

- 不使用、不拥有、也不对目标软件承担任何责任的人；
- 只需要专业代码审查、符号导航或 IDE 内联诊断的资深审查者；
- 希望系统自动替自己批准、合并或发布代码的人。

Change Passport 可以服务开发者，但不能以开发者术语作为所有人的入场券。

## 4. 用户任务

每一份变化报告必须优先帮助用户回答五个问题：

1. 这个软件是做什么的、主要怎样工作？
2. AI 这次主要改变了什么？
3. 谁可能感觉到变化？
4. 哪些事情现在还不能确定？
5. 作为软件负责人，我下一步应该验证什么？

如果用户必须先阅读文件数、代码行数、模块名或框架术语才能回答，产品失败。

## 5. 产品原则

### 5.1 底层可以很深，表面必须极浅

复杂证据不能丢失，但应当通过逐层展开提供，而不是在第一屏展示。

### 5.2 以软件行为为主语，不以代码为主语

优先表达：

> 登录时展示给用户的错误提示发生了变化。

技术证据随后表达：

> 证据来自 `auth.py:82-110`。

除非证据只能支持代码事实，否则不以“某文件影响了某模块”作为主要结论。

### 5.3 技术信息是证据，不是主界面

Diff、模块、imports、symbols、commit 和测试回执应当回答“为什么这么判断”，不能取代“软件发生了什么”。

### 5.4 不知道必须是正式答案

没有运行时、业务配置、部署、数据库、网络或真实用户证据时，页面必须明确说明相应结论尚不能确定。浅显不能以过度推断换取。

### 5.5 同一事实，逐级解释

简单、产品和工程表达必须是同一批已验证事实的不同投影，不能分别生成三套互相漂移的故事。

### 5.6 每出现一个专业术语都要证明其必要性

默认界面只有在“不知道这个词就无法理解软件”时才展示专业术语。否则将它放入技术实现或证据层。

## 6. 信息架构

产品采用三层渐进式披露，而不是从架构图直接进入模块和 import。

### 第一层：软件掌控层

回答：软件如何工作、这次改变了什么、谁受影响、哪里未知、下一步测什么。

语言标准：可以向软件负责人或老板直接解释，不要求代码背景。

### 第二层：解释分析层

回答：为什么这样判断、使用了哪些上下文、结论可信到什么程度、哪些信息互相支持或冲突。

语言标准：可以出现“静态证据”“测试结果”“任务对话”，但仍不要求阅读源码。

### 第三层：技术证据层

展示：Git 范围、Diff、文件、模块、符号、静态依赖、证据引用、测试回执、原始未知项。

语言标准：面向需要复核的开发者和系统。

任何上层结论都必须能够下钻到下层来源；下层事实不能自动升级成上层行为结论。

## 7. 顶层导航

现有：

- `变化解读`
- `整体架构`

调整为：

- `这次改了什么`
- `这个软件怎么工作`

页面内统一提供两个次级入口：

- `为什么这么判断`
- `查看技术细节`

不要求首次用户先理解“架构”“依赖”“基线”“静态关系”等词。

## 8. “这次改了什么”页面

默认顺序固定为：

```text
一句话结论
    ↓
会影响谁 / 风险如何
    ↓
五问解释
    ↓
为什么这么判断
    ↓
技术证据
```

五问仍是完整性合同，但不是五块等权重正文。负责人首先看到能否作决定的结论，再按需要继续阅读。

### 8.1 一句话结论

示例：

> 这次 AI 主要调整了接口说明文字，目前没有代码证据表明核心请求处理方式发生改变。

一句话必须把“确认发生的变化”和“没有足够证据确认的行为”分开。

首屏摘要至少包含：变化属于软件的哪个环节、已确认改变、目前看到的用户影响、仍需验证的边界。抽象规则变化必须紧接一个“以前 / 现在”对比例子；不能要求读者先理解“关系、来源位置、核对版本”等工程概念。

首屏进一步采用“结果在前、内部概念在后”：标题直接说用户能理解的结果，专业概念只作为 `涉及内部` 次级标签。默认只展示十秒内可读完的四项：AI 做了什么、目前用户影响、还需担心什么、负责人现在做什么；完整五问默认收起。

### 8.2 用户能感觉到什么

使用用户、管理员、API 调用方、运营人员或其他项目角色表达，不先使用文件和模块表达。

每个影响对象只能处于以下状态之一：

- `很可能感觉到`；
- `可能感觉到`；
- `暂未发现明显影响`；
- `目前无法判断`。

状态必须显示依据和限制；“没有发现”不能写成“没有影响”。

### 8.3 系统行为变了吗

分开显示：

- 已有证据确认的行为变化；
- 证据支持“暂未发现变化”的范围；
- 未运行、未覆盖或无法静态判断的行为。

### 8.4 哪些地方需要注意

未知项与风险默认可见，不隐藏到技术抽屉。它们应使用普通语言解释“为什么现在不能确定”。

### 8.5 你现在应该测试什么

先给出负责人需要确认的结果，例如“没有真正变化时不再误报”“真正变化时仍能识别”。测试数据如何构造、命令如何运行等执行细节放入“查看详细验证步骤”。

负责人层的验证目标例如：

1. 打开受影响的页面或功能；
2. 完成一次正常操作；
3. 完成一次容易失败的操作；
4. 比较用户看到的结果；
5. 核对仍没有证据覆盖的环节。

每条建议必须标明来源：由已确认变化直接推出、由未知项触发，或来自项目预先声明的验证清单。建议是行动建议，不冒充已经执行的测试。

### 8.6 为什么这么判断

展开后显示：

- 用户原始需求；
- AI 当时的理解或完成说明；
- 用户是否确认；
- Git 与测试证据摘要；
- 结论和来源的对应关系；
- 仍然缺少的证据。

### 8.7 技术细节

最后才展示文件数、增删行、模块、静态依赖、符号和原始 Diff。

## 9. “这个软件怎么工作”页面

第二屏与第一屏分工明确：第一屏帮助负责人判断“这次改动”，第二屏帮助负责人建立“整个软件”的心智模型，并把本次变化标回其中。第二屏不能只是重复第一屏的第一问。

默认阅读顺序固定为：

```text
一句话说明软件怎样把输入变成结果
                ↓
一张从上到下的完整工作图
                ↓
点击并选中一个工作环节
                ↓
右侧解释这一步、当前变化、影响、未知和验证
                ↓
按需查看技术实现
```

### 9.1 软件工作地图

默认是一张可点击、可展开的业务行为图，而不是源码分类图。

示例节点：

- 用户发起请求；
- 系统判断请求属于哪个功能；
- 检查访问权限和运行条件；
- 检查并整理输入数据；
- 执行业务功能；
- 返回结果。

默认隐藏 `router`、`dependency injection`、`Pydantic`、`OpenAPI`、controller、service、repository 等实现词。

工作图必须同时满足：

- 从输入到输出和人的决定边界可以一眼顺着读完；
- 分支与汇合仍以图表达，不降级成等权卡片列表；
- 本次变化只高亮到有直接来源支持的工作环节；
- 多个环节共用一个实现分区时，不得一起推断为已改变；
- 图来自项目声明时，使用短标签说明“项目说明”，不伪装成运行记录。

### 9.2 节点交互

点击业务节点，右侧优先显示：

1. 这个环节对用户意味着什么；
2. 本次变化是否涉及它；
3. 谁可能受到影响；
4. 当前还不知道什么；
5. 建议怎样验证。

右侧默认使用软件负责人语言，并额外显示“这一步会产生什么可见结果”。模块、文件、关系、来源位置和实现分区只在“查看技术实现”后出现。

随后才提供：

- `查看实现方式`；
- `查看技术证据`。

实现方式可继续展开到当前已有的系统分区、实现子域、模块、文件和静态关系。

### 9.3 变化叠加

默认高亮“发生变化的软件环节”，不是“发生变化的文件”。如果代码变化尚不能可靠映射到行为环节，必须显示：

> 已发现代码变化，但目前无法确认它对应哪个用户行为。

### 9.4 图的事实边界

软件工作地图可以来自项目明确声明、已确认任务上下文或经人工确认的候选模型。它不能由静态 import 图自动冒充，也不能单独证明真实运行顺序。

## 10. 输入与来源

### 10.1 确定性技术事实

- 不可变 Git base/head；
- 文件与行级变化；
- 支持的静态模块和关系；
- 实际测试回执；
- 经批准的历史和 baseline。

这些来源可以直接支持技术事实，但不能单独证明业务行为或真实用户影响。

### 10.2 项目声明的产品上下文

- README；
- 产品说明和用户流程；
- 项目配置中的软件工作地图；
- 角色、功能、风险与验证清单；
- 经人工确认的术语和行为映射。

这些内容必须带文件身份、版本和哈希，并与 Git 事实保持独立权威。

### 10.3 任务窗口上下文

沿用 v1.4 的来源区分：

- `用户原话`；
- `AI 回复`；
- `用户已确认`。

如果当前任务窗口已经与变化身份可靠绑定，页面不能直接说“为什么这样改尚不清楚”。它应先提供零 Token 的已有摘录，并可提供用户主动触发的按钮：

> `从任务窗口提炼` · 需要 Token

按钮规则：

- 不在打开页面时自动调用；
- 调用前说明将读取哪些绑定轮次；
- 只读取与当前变化可靠绑定的上下文；
- 结果按输入哈希和提示版本缓存；
- AI 回复不能冒充用户意图；
- 调用失败不能改写成“没有原因”。

### 10.4 AI 解释

AI 可以：

- 把已约束事实改写为不同理解难度；
- 提炼任务上下文；
- 提出候选行为映射和测试建议；
- 解释为什么某项仍然未知。

AI 不可以：

- 添加没有来源的软件行为；
- 把静态依赖说成运行时调用；
- 把可能影响写成已经影响；
- 把自己的完成说明写成测试成功；
- 自动批准 baseline、变更或发布。

## 11. 内部结论模型

界面使用自然语言，但内部必须保留至少四类状态：

| 状态 | 含义 | 默认表达 |
|---|---|---|
| 已观察事实 | Git、测试或其他直接证据确认 | `已经确认……` |
| 有依据的解释 | 多项来源支持，但仍包含解释步骤 | `现有证据表明……` |
| 项目声明 | 来自版本化产品说明或人工确认映射 | `项目说明中定义……` |
| 尚不能确定 | 缺少运行时、业务或匹配上下文 | `目前还不能确认……` |

解释难度不得改变结论状态。简单模式不能省略关键未知项，工程模式也不能把解释升级成事实。

## 12. 解释难度

默认展示最浅层，用户主动下钻，不要求首次设置“技术水平”。后续可以提供：

### 简单表达

> 这次 AI 修改了登录页面的错误提示。没有发现它改变登录验证规则。

### 产品表达

> 登录失败时展示给用户的信息发生了调整；身份校验和登录成功流程暂无明确变化证据。

### 工程表达

> `LoginForm` 的错误展示发生变化；静态证据未发现认证校验路径变化，并识别到 3 个下游引用。

三种表达共享同一结论 ID、来源 ID、状态和未知项。

简单表达不等于删除专业词后继续使用工程抽象。遇到“结构变化”“内部关联”“来源位置”等普通人无法直接对应到软件体验的概念，必须改写为业务结果，或者用相同输入下“以前 / 现在”的不同结果来解释。

界面中的状态正文降为短标签，例如 `已确认`、`暂未发现`、`仍需验证`。完整的证据类型和来源说明保留在解释层。

短标签统一为 `已确认`、`目前没发现`、`还没验证` 等负责人语言，并允许点击查看一句解释。产品必须持续强调：`目前没发现 ≠ 已证明不存在`。

“这个软件怎么工作”默认展示来源合同声明的四步心智模型；点击任一步，四步总览必须继续保留，并在该节点下方展开其完整详细步骤，再次点击可收起。右侧同步解释当前所看步骤，并保持本次变化节点高亮。系统流程图与 change overlay 是默认视觉语言，代码结构图继续作为下层证据。

## 13. 第一阶段范围

PRD v2.0 的第一阶段只验证产品转向是否成立，不追求完整平台。

### 13.1 必须实现

1. 新的五问控制摘要数据模型；
2. 新的两个顶层入口；
3. 以软件行为为节点的工作地图；
4. 业务节点到现有实现分区、子域和模块的逐级下钻；
5. 按用户或系统角色表达的影响视图；
6. 来源明确的“下一步测试什么”；
7. “为什么这么判断”和技术证据抽屉；
8. 同一事实的简单、产品、工程三种投影能力，默认只展示简单表达；
9. 缺少产品上下文时的明确降级；
10. Change Passport 自身样本的独立非技术用户测试。

### 13.2 复用现有能力

- 不可变 Git 证据包；
- 受约束生成器与确定性校验器；
- 任务对话三态和角色来源；
- 目标配置的版本与 SHA-256 绑定；
- 静态结构和变化叠加；
- 单文件、只读、无网络报告；
- 现有实现层下钻和技术证据。

### 13.3 暂不实现

- 自动修改、批准、合并或发布代码；
- 把建议测试自动声明为已执行；
- 无人工确认的通用业务流程发现；
- 云端账号、团队协作、IDE 插件或生产部署；
- 默认上传源码或完整任务对话；
- 为所有框架编写项目专属硬编码规则；
- 以 FastAPI 样本证明普通用户产品理解已经通过。

## 14. 样本策略

### 第一优先：Change Passport 自身

它同时具备：

- 产品目标与 README 素材；
- 明确的任务历史；
- 已知代码变化；
- 可核对的正确答案；
- 快速迭代产生的连续变化。

它用于验证“软件负责人能否理解自己的软件和本次变化”。实现不能针对自身样本写条件分支；所有行为映射必须通过通用合同和版本化项目输入完成。

### 第二优先：具有明确用户流程的外部软件

用于检验业务行为图、影响对象和验证建议能否迁移。

### FastAPI 的角色

FastAPI 继续用于验证：大仓库解析、框架级技术结构、通用布局和证据下钻。它不作为“完全不懂 Python 的人是否理解产品”的首要验收样本。

## 15. 验收标准

### 15.1 第一道人类理解门

找一名不了解目标项目、也不懂目标框架的人。在不接受口头讲解、不打开技术细节的情况下，60 秒内回答：

1. 软件大概怎样工作；
2. AI 这次主要改了什么；
3. 谁可能受到影响；
4. 哪些事情还不能确定；
5. 下一步最应该验证什么。

五问至少四问正确，并且第五问能提出一项与报告一致的可执行验证，才算通过。

### 15.2 事实安全门

- 上层结论 100% 可以追溯到来源；
- 未支持的软件行为结论为 0；
- “没有发现变化”不得呈现为“确认没有变化”；
- AI 回复不得冒充用户确认；
- 建议测试不得呈现为实际测试结果；
- 静态关系不得呈现为运行时调用事实。

### 15.3 行动能力门

用户应能在不阅读源码的情况下：

- 找到最值得亲自验证的环节；
- 说明为什么要验证它；
- 区分已确认、可能和未知；
- 在需要时两步以内进入对应技术证据。

### 15.4 泛化门

至少完成三份评分样本：

- Change Passport 自身；
- 一个具有明确用户操作流程的应用；
- 一个框架或工具型项目。

分别记录理解正确率、Unsupported Claim、下钻成功率和下一步行动质量。单份自举样本或单份 FastAPI 样本不能证明泛化。

## 16. 成功指标

第一阶段优先指标：

- `五问复述通过率`；
- `首次正确理解时间`；
- `未支持行为结论数`；
- `用户能否选出正确的下一步验证`；
- `上层结论到证据的可追溯率`；
- `用户是否需要开发者解释才能完成判断`。

文件数、模块数、图节点数、静态关系数和页面停留时长不是产品成功指标，只是技术或诊断指标。

## 17. 风险与停止条件

### 风险一：通俗化制造虚假确定性

停止条件：无法把业务行为结论绑定到足够来源，却仍然需要确定语气才能让页面“好看”。此时必须降级为未知。

### 风险二：项目配置变成人工重写整个软件

停止条件：每个新项目都必须人工维护完整业务图，成本接近重新写文档。应先验证最小声明、README、任务上下文和代码证据能否协作生成候选图。

### 风险三：继续沉迷架构图视觉细节

停止条件：图的节点、箭头和动画继续增加，但独立用户仍无法回答五问。此时冻结视觉工作，回到语义模型和用户测试。

### 风险四：把测试建议当成安全保证

停止条件：页面让用户误以为完成建议步骤即可证明整个软件安全。建议必须保留范围和未知边界。

### 风险五：解释层与证据层漂移

停止条件：简单、产品和工程模式产生不同事实、状态或遗漏关键未知项。

## 18. 实施顺序

本 PRD 获得确认后，按以下顺序另立实施任务：

1. 冻结五问数据合同、来源矩阵和降级规则；
2. 使用 Change Passport 自身事实制作无新 UI 的文本样本；
3. 做第一次独立非技术复述测试；
4. 根据失败点修正语义模型；
5. 设计新的首页和软件工作地图交互；
6. 实现确定性投影、受约束 AI 接口和技术下钻；
7. 对 Change Passport、用户型应用和框架型项目完成三样本评分；
8. 通过理解门后再决定产品集成、自动任务窗口连接或发布形态。

不应先继续扩展图形功能，再等待用户研究证明它有用。

## 19. 与现有版本的关系

保留：

- 确定性证据主干；
- 受约束生成与校验；
- unknown 和 authority 边界；
- 目标项目只读；
- 项目配置可追溯；
- 技术架构与实现下钻；
- 任务窗口三态合同。

改变：

- 默认用户从代码阅读者改为软件负责人；
- 默认主语从代码实体改为软件行为；
- 默认首页从变化数据改为五问掌控摘要；
- 架构图从源码入口改为软件工作地图；
- 影响从 impacted files 改为谁可能感觉到变化；
- 输出从“解释完成”改为“帮助用户决定下一步验证”。

冻结：

- 在 PRD v2.0 未确认、五问数据合同未冻结前，不继续增加架构图布局、动画或技术节点；
- 不以当前 FastAPI 页面作为产品方向已经通过的证据；
- 不启动远端模型、任务系统连接器、提交、推送、打包、部署或 baseline 批准。

## 20. 确认门

产品负责人确认本 PRD 后，只代表确认产品方向、第一阶段范围、事实边界和实施顺序。实施工作仍需形成独立的有界任务计划；本确认不授权提交、推送、部署、远端模型调用、任务账号读取或 baseline 批准。
